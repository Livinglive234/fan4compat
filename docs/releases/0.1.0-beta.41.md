# Fan4Compat 0.1.0-beta.41

First fixes from running beta 40 on a real dedicated server with two clients.

**Shared map.** Terrain explored by one client reached the other only in part. Three causes, all fixed:
- The client told the server its progress as "the newest stamp I applied", so one chunk applied later than an older one that was still waiting (or had been
  dropped) made the server stop sending that older one, for good. Progress now never passes a chunk that was not written: a chunk that is queued, waiting
  for its region, dropped because the queue was full, or for a dimension that was not shown, holds it back, and the server sends it again next time. (Your
  saved progress files are still valid; they just stop skipping chunks from here on. Delete `fan4compat/shared-map/<server>.properties` in the game
  folder to make the server send everything again.)
- Terrain in a map region Xaero had not loaded could never be written. Xaero's own writer creates the region and asks for it to be loaded; the shared map
  now does the same, at most one region per frame and four at a time, and writes the terrain once it has loaded. The data is saved by Xaero with the rest of
  your map.
- Chunks waiting for a region were tried only about twelve times a second; they now get a place every frame (more when nothing new is arriving).

**Water.** Uploaded water showed as bare lake bed, and server-captured water was drawn as a flat block. Xaero stores water as an overlay on the bed block (its
opacity is the depth); summaries now carry the block under the water as well, and the client writes water the same way Xaero does, through Xaero's own overlay builder.
The upload reader takes the overlay as the top block and the base block as the bed. Chunk batches are version 2 (version 1 batches and region files from older builds are
still read, just without beds); the server refreshes water columns as it re-sees them. Shared tiles already written into a client's Xaero map as plain water stay
until Xaero replaces them with real data (it does so the first time you load that chunk yourself).

**Waypoint sync.** Waypoints edited while playing were never uploaded: joining reset the sync client that the join had just set up, so the upload timer
never started. Fixed, with a regression test. Waypoints that did not arrive when joining: found with the diagnostics below. During the join the game has not yet recorded
which server it is connecting to, so the client could not tell which Xaero folder to sync ("server address null") and silently did nothing on every join. The address
now comes from the connection's own server entry (the address Xaero names its folder after), falling back to the connection's host.

**Where the client keeps its data.** Fan4Compat's own Xaero state (the shared map's progress per server, the waypoint sync's state and backups) is now in a visible
`fan4compat` folder in the game folder instead of a hidden `.fan4compat-xaero`. On first use an existing hidden folder is renamed, so nothing saved is lost.

**Diagnostics.** The "Xaero TARDIS diagnostics" switch is now "Xaero diagnostics" (`xaeroDiagnostics`, off by default, immediate). Besides the TARDIS lines it
logs, as `[Fan4Compat XaeroDiag]`: the shared map client's queue and progress every ten seconds or so, and each step of the waypoint exchange on both the
server and the client (who joined, whether the client can take part, what the server sent, which folder the client found, what it sent back, what the server
accepted or refused). Turn it on for the client and the server and send the `latest.log` of both.

Validation: clean build, all tests (the shared map tests cover the new progress rule, region requests and their limits; the sync flow test covers the upload
fix) and the real-jar native checks, which now include the calls used to load a region. Not run in game: the region requests inside real Xaero.
