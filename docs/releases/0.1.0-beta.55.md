# Fan4Compat 0.1.0-beta.55

**The Fan4Compat jar can now fix the Sodium 0.8 startup error itself.** With Sodium 0.8.13 and Iris 1.8.14-beta.1 installed, Immersive Portals' own metadata makes Fabric Loader refuse to start ("Incompatible mods found"). Fabric Loader stops
before it loads any mod, so Fan4Compat cannot show anything from inside the game. The jar is now also a small program, run two ways. Both need the Fan4Compat jar to be in the `mods` folder of the instance you want to fix (the tool looks for Immersive Portals beside itself, and the Java argument points into `mods`):

- **Double-click it** (or `java -jar Fan4Compat-….jar`). If it finds an Immersive Portals jar in the same `mods` folder that conflicts with the installed Sodium or Iris, it shows the message *"Immersive Portals must be modified to work with
  Sodium 0.8.13 and Iris 1.8.14-beta.1. Fan4Compat can modify your Immersive Portals jar for you, or you must downgrade your Sodium and Iris versions to 0.6.7 and 1.8.1 respectively. NOTE: Downgrading versions will require you to
  reinstall all Sodium related mods to a supported version."* with two buttons: **Patch Immersive Portals** (removes the `iris` and `sodium` entries from the jar's `breaks`, keeps everything else, and moves the original to
  `.fan4compat-backup` beside `mods`) and **Show downgrade list** (each installed Sodium, Iris, Sodium Extra, Reese's Sodium Options and More Culling with the version it needs on Sodium 0.6.7, and that Sodium Options API must be
  reinstalled; each mod name links to that exact version on Modrinth, and Fabric Loader 0.19.5 is named as enough for the old versions). Windows often opens .jar files with Java 8, which cannot load Fan4Compat, so the jar's Main-Class is a small Java 8 launcher that starts the jar again with Java 17 or newer (found in `JAVA_HOME`, Prism's Java folder, Program Files, `/usr/lib/jvm` and similar) and explains what to do if there is none. With no conflict it does nothing. Without a display it prints the message; arguments `patch`, `list` and a mods folder path work from the command line.
- **As a Java agent**, `-javaagent:mods/Fan4Compat-….jar` in the instance's Java arguments runs the same check before Fabric Loader starts, so the question appears at launch. After it patches the jar the game keeps starting by itself (the double-click version tells you to start the game). It never stops the launch on a failure, does nothing when there is
  no conflict, and takes `=patch` to edit the jar without asking (servers). On macOS the question is asked through AppleScript, because the game's process cannot use AWT there. If the jar is renamed, remove the argument or Java will not start.

Nothing changes for the game itself: this code only runs when the jar is started directly or as an agent. The Sodium Options API is not removed for you (the dialog and the README say so), and Fabric Loader 0.20.1 is still needed for Sodium 0.8.

**Sable 2.0.6 beside Immersive Portals and Valkyrien Skies.** These fixes only work when Fan4Compat is already in the `mods` folder (client and server) next to Sable, Immersive Portals and Valkyrien Skies: they are applied while the game loads, so without Fan4Compat the game still stops at start. With all three installed, the game stopped on start: Mixin refuses when two mods change the same call, or when one injects into a method another has replaced. Three
clashes are handled, each under its own switch (on by default, restart to change):
- **Entity collision** (`sablePortalCollision`): both Immersive Portals and Sable redirect `Entity.collide` in `Entity.move`. Sable's redirect now runs inside Immersive Portals' collision handler, so Immersive Portals' checks and portal
  collision come first, then Sable's collision with its sub-levels, then the plain collide. Done with MixinSquared's annotation adjuster; neither mod's code is copied.
- **Player fit check** (same switch): Immersive Portals replaces `Player.canPlayerFitWithinBlocksAndEntitiesWhen` with an `@Overwrite`, and Sable wraps a call inside it, which Mixin forbids at equal priority. Fan4Compat's replacement of that
  method (same body, lower priority) takes its place and Sable's wrap applies to it.
- **Bed placement** (`sableSleeping`, Sable with Valkyrien Skies): Sable replaces `LivingEntity.setPosToBed` and redirects the stand-up `setPos`; Valkyrien Skies' bed fix wraps both. Its two clashing wraps are skipped, so while both mods
  are installed Valkyrien Skies' own bed placement on ships is not applied (Sable's is). Its third hook is untouched.
Verified: build, tests (including a replay of MixinSquared's own annotation walk) and a check against the real Sable and Immersive Portals jars. In game on a Mac with Sable 2.0.6, Create Aeronautics, Simulated, Offroad, Immersive Portals and
Valkyrien Skies, Mixin gets past all three; that instance then stops on a separate failure inside the Simulated mod (its comparator hook finds no target), which is not caused by Fan4Compat. Collision and sleeping behaviour are not yet
tested in play.

Validation: clean build and all tests, including a new one that builds mods folders with fake jars (no conflict with Sodium 0.6.7 / Iris 1.8.1, conflict with 0.8.13 / 1.8.14, exact dialog text, downgrade list, patch keeps every other
entry and escape, original backed up outside `mods`, no temporary files, repeat runs change nothing). Run from the command line and as an agent against the real Immersive Portals 6.0.6 jar with the real Sodium 0.8.13 and Iris 1.8.14 jars:
the conflict is reported, the jar is patched, the second run reports nothing. **Not tested:** the graphical dialog's buttons (a window opened on a Mac, buttons not clicked), the macOS AppleScript dialog, Windows and Linux dialogs, and the
agent inside a real launcher.
