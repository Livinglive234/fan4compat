# Fan4Compat 0.1.0-beta.50

**Spatial GUI next to Immersive Portals: the Spatial GUI screen is no longer drawn with the portal's camera.** Spatial GUI saves the projection and view matrices after every world render so it can place its screen in the world, and
Immersive Portals renders each portal view as a further world render after the main one, so with a portal loaded nearby the saved state belonged to the portal and the screen rendered wrongly (a slice of the world dragged over the
portals on the first frame, JEI's bottom-left buttons showing on the real window). The new **Spatial GUI keeps its screen steady beside portals** switch (`spatialGuiPortalFix`, on by default, restart to change) skips that save
while a portal view is rendering, so only the main view sets it. It applies only to Spatial GUI 1.9.1 together with Immersive Portals. The screen was confirmed drawing correctly over portals on the owner's PC.

**Known, not fixed here:** portals still go blank (or show the wrong view) while a Spatial GUI screen is open. Spatial GUI moves the camera to its own view of the player and Immersive Portals sets up the portal cameras at the
same point, so the two disagree. A fix is planned for beta 51.

**New troubleshooting switch: Spatial GUI portal diagnostics** (`spatialGuiDiagnostics`, off by default, restart to change). While a Spatial GUI screen is open it logs `[Fan4Compat SpatialGuiDiag]` lines (world render nesting
and portal layer, bound framebuffers, Spatial GUI's target and flags, and the camera's position and angles) for the first 160 stages after the screen opens. It changes nothing. Applies only to Spatial GUI 1.9.1 with Immersive Portals.

Validation: clean build, all tests (the probe logic, the skip rule, the exact-version and feature gates) and a real-jar check of every Spatial GUI and Minecraft member the hooks and the trace use (Spatial GUI 1.9.1). Run in game on a
Windows PC with Spatial GUI 1.9.1 and Immersive Portals 6.0.7: the trace and the matrix fix.
