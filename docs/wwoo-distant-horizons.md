# WWOO / Distant Horizons grid investigation (withdrawn experiment)

Inspected: WWOO Fabric 2.6.7 and Distant Horizons 3.3.3 for Minecraft 1.21.1.
The user's logs include DH's explicit warning about WWOO LOD section grid lines.

## Evidence and candidate fix

WWOO contains cross-chunk terrain decoration, including vanilla disk features.
DH's `DhChunkGenerator.generateChunks` reads
`MAX_WORLD_GEN_CHUNK_BORDER_NEEDED`, initialized to zero in the inspected build.
It constructs four overlapping odd-sized generation regions for an even-sized
request and returns only the original requested chunks. StepFeatures generates
features for the region's chunks, with block writes constrained to that region.
An absent neighbour context is a plausible cause of cut-off terrain decoration;
it has not been established as the cause of every visible grid artifact.

Alpha 34 redirects only the per-event border read: zero becomes one for
Overworld FEATURES requests whose target step is FEATURES. Existing nonzero
padding is preserved. Both mod versions are gated before applying the mixin.
The native region allocation and feature pipeline do the remaining work. No
static border field, worldgen data pack, real-world chunk loading API, or user
DH configuration is changed. The extra chunks are transient generation context.
The original output coordinates and callback area remain native.

This increases generation work. For a 16-chunk-wide request, each of the four
native regions grows from 15 x 15 to 17 x 17 slots, about 28% more slots before
reuse or existing-chunk shortcuts. Smaller requests have a higher relative cost;
this is not a measurement of CPU time. Full Minecraft chunk generation and
permanent chunk tickets are not enabled.

## Experiment withdrawn in alpha 35

The pack owner requested removal because visual benefit had not been established
and the extra generation work was not justified. Alpha 35 removes the helper,
mixin, generator, version gate and experiment-specific tests. No WWOO generation
patch is active. The `fan4compat.wwooBorder` switch no longer does anything.

Alpha 34 passed standalone checks of the border scope, native allocation math
and a simplified cross-border feature fixture. Those checks did not run
Minecraft or prove that the reported full-pack grid lines would disappear.
WWOO / DH grid seams remain unresolved; no LOD cache or DH user configuration
was changed during either implementation or removal.

## Upstream verdict and further analysis (2026-10-10)

Investigated against WWOO Fabric 2.6.7 and DH 3.3.3 (decompiled DH 3.3.3
generation classes; WWOO jar contents). Nothing in the addon changed.

### Distant Horizons considers this unsupported

DH issue [#1137](https://gitlab.com/distant-horizons-team/distant-horizons/-/issues/1137)
("William Wythers' Overhauled Overworld", closed 2025-12-20) concerns the same
startup warning. A DH contributor replied that it is a warning, not a bug: WWOO is
incompatible with the default FEATURES generator, improving that generator would
slow it down and add complexity, and the options are to use the FULL generator,
remove WWOO, remove the incompatible WWOO features, or ignore the visual bug. DH's
lead developer confirmed this and closed the issue. Upstream will not fix it.
The wiki says to set the generator mode to `Full` or `INTERNAL_SERVER` for real
chunk generation. That mode's code path has not been inspected here.

### What WWOO contributes

WWOO is a datapack (five Java classes, no rendering code). Of its 481 placed
features, 189 are disks (113 with radius 6-8, up to 256 placements per chunk) and
41 are ore-style repaints (29 of size 64, 50-100 placements per chunk). They repaint
ground blocks (stone to andesite, dirt to coarse dirt, sand and gravel patches, and
similar), and some predicates sample blocks at +/-1 offsets. A size-64 vein can
reach roughly 13 blocks from its origin, past a chunk edge. Vanilla uses far fewer
such features.

### DH generation mechanics (3.3.3)

- Each DH section is an independent generation event of W x W chunks.
- `generateChunks` runs four overlapping (W-1) x (W-1) regions offset by one
  chunk. The border is 0 for every step (`MAX_WORLD_GEN_CHUNK_BORDER_NEEDED = 0`).
- A chunk already at FEATURES status is skipped
  (`AbstractWorldGenStep.getChunkWrappersToGenerate`), so each chunk gets features
  once, in the first region containing it.
- The region subclasses vanilla's `WorldGenRegion`. Writes outside it are presumed
  rejected; the vanilla write check was not verified (no Minecraft jar).

Consequences, as a hypothesis consistent with DH's warning but not confirmed in game:

- Feature spill across a section boundary is clipped, and chunks outside the event
  never run their features to contribute spill back.
- Inside an event, the last chunk column and row are generated by an earlier region
  where they sit on the edge, so their spill into the final column/row is also
  dropped. This suggests a second seam one chunk inside the east and south edges,
  which the alpha 34 notes did not describe.
- Padding regions by one chunk (alpha 34) adds context chunks only. Their features
  do not run, so it cannot supply the missing spill.

### Other causes and settings to rule out

- DH's FAQ attributes flat-LOD grid lines to compression. Setting
  `Advanced -> LOD Building -> Lossy World Compression` to `Merge Same Blocks` and
  regenerating the affected LODs removes them. This is not WWOO-specific.
- Switching the distant generator mode to `SURFACE` skips features and works as a
  diagnostic: if the seams vanish, features are the cause.
- `INTERNAL_SERVER` (Full) is the upstream-recommended workaround. It generates real
  chunks, so it costs more time, CPU and disk.
- DH issue [#1339](https://gitlab.com/distant-horizons-team/distant-horizons/-/issues/1339)
  (open, 2026-10-08, DH 3.3.3) reports wrong LOD biome colors with the WWOO datapack.
  It is a separate problem from the grid lines.

### Status

No in-game test of any setting above has been run. The seams remain an unresolved
upstream limitation with no active Fan4Compat fix.
